CORE IDENTITY MODEL
-------------------
DO NOT bind a Facebook account to "LD-01".

There are two separate concepts:

1. Runtime Device
   - LDPlayer instance
   - MuMu instance
   - Physical Android phone/tablet
   - Temporary execution host

2. Account Environment Profile
   - Persistent account-linked configuration
   - App channel/package/version
   - Locale/language
   - Timezone
   - Display configuration
   - Network profile
   - Optional QA/test location profile
   - Permission profile
   - Notification profile
   - Secure session/app-state references
   - Environment revision history
   - Last runtime/restore/backup metadata

Correct runtime flow:

Account
  ↓
Load Account Environment Profile
  ↓
Find compatible Runtime Device
  ↓
Reserve device
  ↓
Prepare device
  ↓
Apply safe environment through companion app / normal supported settings
  ↓
Restore permitted secure state if enabled
  ↓
Health check
  ↓
Run authorized workflow
  ↓
Persist result/runtime history
  ↓
Optional safe state backup
  ↓
Cleanup
  ↓
Release device

ENGINEERING RULES
-----------------
1. Python package: src/spfarm.
2. PySide6 UI contains no business logic.
3. UI never directly calls SQL, requests, subprocess, adb or Appium.
4. Domain never imports PySide6/SQLAlchemy/requests/Appium.
5. Every long operation runs off the UI thread.
6. Use QTableView + QAbstractTableModel for large data.
7. SQLite + SQLAlchemy 2 + Alembic.
8. Enable SQLite WAL.
9. Use UUID internal IDs.
10. Structured logging with correlation IDs.
11. External integrations behind interfaces.
12. Device operations support timeout/cancellation.
13. Jobs are persistent and restart-safe.
14. Prefer official Meta APIs where supported.
15. Mobile automation uses versioned selector registry.
16. Avoid god classes.
17. Add tests every phase.
18. Support Python 3.13+; test 3.14 only where dependencies support it.
19. Secrets never enter Git.
20. Runtime data is not stored in repository root JSON files.
